# Архитектура Lumen

## Слои

| Слой | Файл | Ответственность |
|---|---|---|
| Криптография | `core/crypto.ts` | ed25519, SHA-256, base58check-адреса |
| Состояние | `core/ledger.ts` | счета, транзакции, стейкинг, AMM, state root |
| Консенсус | `core/chain.ts` | блоки, Merkle, продюсер по весу, финальность 2/3 |
| Транспорт | `core/rpc.ts` | JSON-RPC + кошелёк + подпись транзакций |
| P2P | `core/gossip.ts` | соседи по `peerId`, рассылка блоков, догоняние цепочки |

## Генезис

`chain.genesis()` чеканит всю эмиссию (1e9 LMN) в два счёта: 60% — казна,
40% — пул ранних валидаторов (выплата 1:1 за стейк). Адреса выводятся из
фиксированных seed-строк, поэтому любой узел получает одинаковое состояние
генезиса и одинаковый `stateRoot`.

Время генезис-блока фиксировано (`GENESIS_TIMESTAMP`), а не берётся из часов:
хэш генезиса входит в `prevHash` первого блока, поэтому локальное время сделало
бы генезис разным на каждом узле и gossip-сеть не сходилась бы (`bad prevHash`).

## P2P gossip (`core/gossip.ts`)

| Что | Как |
|---|---|
| `peerId` | `sha256(публичный ключ)` — 64 hex-символа |
| Объявление | `announce()` рассылает `peerId`, высоту, хэш генезиса и список соседей |
| Рассылка | успешный `GossipNode.accept()` немедленно шлёт блок всем соседям |
| Догоняние | блок выше `height + 1` → `wantBlocks` → переигровка через `chain.accept` |
| Повторы | хэши принятых блоков в `seen`, ретрансляция уже известного хэша прекращается |
| Чужие сети | сосед с другим `genesisHash` отбрасывается (`rejectedPeers`) |

Транспорт — интерфейс из двух методов (`send`, `broadcast`), поэтому ядро
не зависит от сети: `MemoryNetwork` для тестов, `node:net` в реальном узле.

Принятый из сети блок проходит ровно те же проверки `chain.accept()`, что и
локально предложенный: высота, `prevHash`, продюсер из набора валидаторов,
подпись, хэш блока, Merkle-корень. Невалидный блок от соседа отвергается и
не ломает узел (счётчики в `stats`, текст причины в `lastError`).

## Транзакция

```jsonc
{
  "from": "lmn1…", "to": "lmn1…", "amount": "1000000",
  "fee": "1000", "nonce": 3, "data": "", "timestamp": 1763000000000,
  "signature": "base64(ed25519)"
}
```

Подписывается каноническая строка `from|to|amount|fee|nonce|data|timestamp`.
Значение `data` задаёт тип операции: `stake:` / `unstake:`.

## Блок

```
header: { height, prevHash, timestamp, proposer, merkleRoot, txCount, slot }
txs:    Transaction[]
signature: base64(ed25519 от ключа продюсера)
hash:   sha256(header)
```

Применение блока проверяет: высоту, `prevHash`, подпись продюсера, хэш блока,
Merkle-корень и каждую транзакцию (подпись, nonce, баланс).

## Консенсус

- Продюсер слота выбирается детерминированно: веса stake, точка = slot × totalStake.
- Награда: 3% годовых от общего supply, начисление за каждый предложенный блок.
- Финальность: блок финализирован, когда подтверждён весом ≥ 2/3 от total stake.

## AMM

Постоянное произведение: `out = (quote × effIn) / (base + effIn)`, где
`effIn = in × (1 − 0.3%)`. Комиссия остаётся в пуле — это доход LP.

## State root

`sha256` от отсортированного списка `адрес:баланс:стейк:nonce` — детерминированный
корень состояния, по которому узлы сверяются.

## Что осознанно не сделано

| Не сделано | Почему |
|---|---|
| Смарт-контракты в самой цепи | слишком большой объём для первого релиза; VM появится в v0.2 |
| Шардинг | не нужен при 1e9 supply и PoS |
| Сложная криптография (ZK) | ed25519 + SHA-256 достаточно и аудируемы |
| Реализация транспорта на `node:net` | gossip-слой определён через интерфейс `Transport`; реальный транспорт — отдельный PR |
